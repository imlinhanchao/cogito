# Tellory 互动故事创作

Tellory 故事的读者既是读者也是玩家。写作质量看两件事：段落正文是不是值得读完的中文，选择是不是真的改变了什么。这两件事分别对应下面两类材料，缺一不可。

## 先读哪些材料

1. **语法权威来源**：[reference/story-syntax.md](reference/story-syntax.md)（复制自仓库 SYNTAX.md）。动笔前重新读一遍全文，不要凭记忆写宏。若仓库根目录的 SYNTAX.md 已更新，先同步一份到这里再动笔。本文件里的语法速查只是提醒，冲突时以 reference/story-syntax.md 为准。
2. **叙事技艺**：读取 [reference/fiction-craft.md](reference/fiction-craft.md)，按其中"先给人物一件眼下要办的事""性格藏在选择里""对白在做事""设定等人物碰到再讲""结尾留下后果"几节来写人物、场景与对白。用户要第一人称帖子体故事时，再读 [reference/forum-prose.md](reference/forum-prose.md)。
3. **成稿自查**：写完段落正文后，按下面"成稿禁用清单"自查一遍。段落正文是给玩家看的中文，同样不能有模型腔。可用 `scripts/check_prose.py` 检查纯文本段落：`python3 scripts/check_prose.py <稿件路径>`。
4. **结构与渲染验证**：见下方"结构与渲染验证"一节，写完故事源码后必须跑一遍。

### 成稿禁用清单

命中一项就不能交稿，覆盖标题、段落正文与选项文字：

- 不写翻案腔："不是……而是……""并非……而是……""看似……实则……""表面……实际……"及同类变形。判断直接正面下，先给结论再给依据。
- 不写三项以上的同构排比，两项为限。
- 不给抽象名词配具体动词抒情（"时间不会保管细节"一类）。
- 不把动词名词化（"进行了赋值"写成"赋了值"）。
- 不用破折号 `—`、`——`、`–`。
- 冒号只用于引出人物原话，不用作"一句话总结："这类提示语。
- 不用"说白了""说穿了""先说结论""更微妙的是""值得注意的是"这类路标词。
- 不用赋能、抓手、闭环、拉通等商业/模型黑话包装剧情。

## 选择才是最小叙事单位

互动小说和线性小说的核心差异在这里，是写作时最容易漏掉的一步。

- 每一次分支要像 [reference/fiction-craft.md](reference/fiction-craft.md) 里"每场戏结束时改变一点东西"：至少改变信息、关系、风险、资源或人物对局势的认知中的一项。两个选项如果最终导向同一段文本、只是路引文字不同，这不算真分支，删掉其中一个或者改回线性段落。
- 用变量（`$变量`）记住真正影响后续内容的状态：好感度、有没有拿到钥匙、说过的谎、剩余资源。不要为了显得"系统化"给不影响任何后续文本的东西建变量。
- 关键选择、秘密暴露、无法撤回的动作要用完整段落慢下来写；纯粹的路径切换（"去 A 还是去 B，两边都是空白的搬运"）可以概述过去，不必每个岔路都写成完整场景。
- 分支设计避免车祸、双胞胎、临时新规则这类救场手法（同 reference/fiction-craft.md），除非这条规则在更早的段落里已经铺垫过。

## 段落与宏语法速查

以 [reference/story-syntax.md](reference/story-syntax.md) 为准，这里只列高频写作要点：

- 段落头 `:: 段落名`（可选 `:: 段落名 [标签1,标签2]`），段落名在全故事内唯一，`[[...|目标]]` 和 `(goto:)` 引用的名字必须真实存在，否则是死链接。
- `(set: $变量 to 表达式)` 写在段落正文里会在**进入段落时**立即执行；附着在链接后面，如 `[[开门|Hall]](set: $hasKey to true)`，才会在**点击那一刻**执行。两者用途不同，别混。写"先赋值再跳转"的效果，必须把 `(set:)`/`(call:)` 直接跟在 `[[...]]` 或 `(link:)[...]` 后面/内部。
- `(point: 名称|描述)`：用于在渲染时生成成就/提示徽章。作为段落内独立宏时（非链接附着）会在进入段落时加入当前渲染的点队列，渲染结果会在页面顶部以徽章形式显示；如果把 `(point:)` 附着到链接上（例如 `(link:"查看钥匙")[(point: 金色钥匙|描述)]`），则该点只有在点击链接时入队并在下一次渲染显示。可用于提示玩家获得物品或达成小成就。
- `(end: 名称|描述)`：用于标记结局。只有当段落不包含任何可点击链接且该段落仅包含一个 `(end:)` 时，该标记才被视为有效结局并在页面底部显示结局徽章。若需要通过点击触发结局，请把结局放在独立结局段落并由链接导航或 `(display:)` 展示。
- 条件分支 `(if: 条件)[ 文本 ](else-if: 条件)[ 文本 ](else:)[ 文本 ]`，括号与条件之间要留空格。比较关键字用 `is`/`is not`/`eq`/`ne`/`contains`，不要写 `==`/`!=`。
- 变量默认值是数字 `0`。用作字符串或布尔状态的变量，第一次使用前要在起始段落或更早处先 `(set:)` 好初始值，否则条件判断会因为类型不对而出错。
- `(fn:"name")[JS代码]` 会以 `new Function('vars','args', code)` 执行任意代码，仅在受信任的创作环境使用，不要把玩家输入原样拼进去执行。
- `(display: "段落名")` 用于复用片段（如状态栏、常驻提示），不要用它拼接大段主线剧情，否则分支结构会读不出来。

### 查看/对象提示建议

对于“查看某物/查看对象”这类交互，建议把对象描述写成独立段落（例如 `:: Key`），但**在正文中自然嵌入链接**来触发查看，而不要把“查看 XXX”作为页面底部或选项列表单独列出。

示例：

- 在段落中自然嵌入（推荐）：

  捡到了一把[[钥匙|Key]]，你可以试着把它放进口袋。

- 如果只需在当前上下文展示简短提示，可用判断结合 `(display:)` 内联呈现：

	捡到了一把钥匙，(link:"查看钥匙")[(display:"Key")]。

将对象描述做成独立段落可以实现复用，也便于审计脚本检测死链/孤立段；但链接应保持自然内嵌以维护阅读流与语境。

## 结构设计建议

- 收敛与发散：多数互动故事用"hub and spoke"或"树状带汇合点"结构，让分支在关键节点重新汇合，避免分支数量指数爆炸到无法维护。
- 每个结局段落都要留下确定后果（人物的新位置、关系的新状态、一件已经无法撤回的事），不要用暧昧收尾同时糊弄多条分支线，参考 reference/fiction-craft.md 的"结尾留下后果"。
- 写完一条主分支后，检查是否有孤立段落（没有任何链接指向）和死链接（`[[...|X]]` 指向不存在的 `X`）。

## 结构与渲染验证

写完故事源码后，先跑这两个脚本，再交付。两个脚本互相独立，检查角度不同。

- `python3 scripts/audit.py <故事文件>`：纯文本结构审计，不依赖 SDK。检查段落名是否重复、`[[...|目标]]`/`(goto:)` 是否指向存在的段落（死链接）、是否存在没有任何链接指向的孤立段、从 `Start` 出发是否能到达全部段落、变量是否存在“引用但从未 `(set:)`”的情况。
- `node scripts/smoke.cjs <故事文件>`：真实调用 `tellory` SDK 解析故事，并在多组变量配置下逐段调用 `renderStoryText` 渲染，检查是否有段落渲染为空、渲染结果里是否残留未展开的宏记号（如 `(if:`、`[[`）、渲染过程是否抛异常。需要先在项目里安装 `tellory`（`npm install tellory`），脚本内的示例变量结构（`base`/`configs`）要按当前故事实际使用的变量名改写，否则测不出真实分支。

两个脚本都发现问题时先修故事源码，不要去改脚本本身的判定逻辑迁就问题文本。

## 交付

- 只交付故事源码本体（段落文本+宏），不展示创作过程、分支大纲或语法自查记录，除非用户要。
- 交稿时说明已运行 `audit.py`/`smoke.cjs` 的结果；仍提醒用户在编辑器里试玩一遍关键分支，确认变量状态和跳转符合预期，尤其是"链接后置 set/call"这类容易写反的地方。
